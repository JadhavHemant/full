# 7. Impact Classification

Classify every identified effect as one of the following.

## DATABASE-AUTOMATIC

PostgreSQL guarantees the effect because of:

* Foreign-key cascade.
* Foreign-key set-null rule.
* Generated column.
* Check constraint.
* Unique constraint.
* Trigger.
* Stored procedure.

## APPLICATION-REQUIRED

The backend must implement the effect through:

* Controller.
* Service.
* Repository.
* API.
* Event handler.
* Queue worker.
* Scheduled job.
* Transaction function.

## APPROVAL-REQUIRED

The operation must remain pending until an authorized approver approves it.

## PERMISSION-DENIED

The user does not have the required role, permission, scope, ownership, or warehouse access.

## REPORTING-ONLY

The source records do not change, but reports, dashboard totals, search results, or analytics are affected.

## POSSIBLE-RISK

The schema implies that a change should occur, but the required constraint or application logic is missing or unclear.

## NO-EFFECT

The table or record should not be changed by the requested operation.

# 5. Access-Control Decision Order

Evaluate access in this exact order.

## Step 1: Authentication

Confirm:

* The user exists.
* The user is active.
* The user is not deleted.
* The session or token is valid.
* The user belongs to an active company.
* The account has not been locked.

If authentication fails, deny the operation immediately.

## Step 2: Company scope

Check:

* The record’s `CompanyId`.
* The user’s company memberships.
* Whether the role permits cross-company access.

Default rule:

A user must not view or modify records belonging to another company.

Super Administrator access must be explicitly identified and audited.

## Step 3: Branch scope

Where `BranchId` exists, verify that the user is assigned to the branch or has company-wide access.

Default rule:

A branch-level user may access only records belonging to assigned branches.

## Step 4: Warehouse scope

Where `WarehouseId`, source warehouse, or destination warehouse exists, verify access to the relevant warehouses.

For stock transfers:

* The creator must have permission to request a transfer.
* The source warehouse user must have dispatch permission.
* The destination warehouse user must have receive permission.
* A user should not receive stock into an unauthorized warehouse.
* Cross-company warehouse transfers must be rejected.

## Step 5: Module permission

Check whether the user has permission for the module and action.

Example:

Changing a stock-adjustment record requires more than generic update permission. It may require:

* `inventory.stock.adjust`
* `inventory.stock.adjust.approve`
* Warehouse access.
* Quantity-limit approval.
* Reason entry.

## Step 6: Record-level visibility

Check whether the user can access the individual record through:

* Ownership.
* `CreatedBy`.
* `AssignedTo`.
* `AssignedFrom`.
* Group membership.
* `EntityVisibility`.
* Company-wide role.
* Department hierarchy.
* Manager-subordinate relationship.
* Explicit sharing.
* Approval assignment.

For CRM records, apply visibility rules such as:

* Private.
* Owner only.
* Assigned user.
* Group visible.
* Company visible.
* Public within company.

## Step 7: Field-level permission

Check whether the user may edit the specific field.

Examples of sensitive fields:

* Product cost.
* Selling price.
* Discount.
* Tax rate.
* Credit limit.
* Outstanding balance.
* Payment status.
* Approval status.
* Stock quantity.
* Reserved quantity.
* Warehouse ID.
* Company ID.
* CreatedBy.
* UpdatedBy.
* IsDeleted.
* DeletedAt.
* User role.
* Salary.
* PAN.
* Aadhaar.
* Bank details.

A user may have permission to edit a record but not these sensitive fields.

## Step 8: Status-transition permission

Validate that the requested status transition is allowed.

Example:

* Draft to Pending.
* Pending to Approved.
* Approved to Processing.
* Processing to Shipped.
* Shipped to Delivered.
* Approved to Cancelled.
* Received to Cancelled through reversal only.

Reject invalid status jumps.

## Step 9: Approval requirement

Determine whether the action requires approval based on:

* Transaction value.
* Quantity.
* Discount percentage.
* Stock-adjustment reason.
* Negative stock.
* Cross-warehouse transfer.
* Cross-branch transfer.
* High-value purchase order.
* High-value sales return.
* Payment amount.
* Expense amount.
* Product cost change.
* Credit-limit change.
* Record deletion.
* Backdated transaction.

## Step 10: Segregation of duties

Check whether the same user is improperly performing conflicting actions.

Examples:

* Requesting and approving the same purchase order.
* Creating and approving the same stock adjustment.
* Creating and receiving the same stock transfer.
* Creating and approving the same expense.
* Creating and approving the same payment.
* Creating and approving the same sales return.
* Editing and auditing the same transaction.

If segregation of duties applies, require a different user for approval.

Identify the directly changed table and all dependencies.

For every relationship, determine:

* Parent table.
* Child table.
* Foreign-key column.
* Relationship direction.
* Cardinality.
* Delete behaviour.
* Update behaviour.
* Whether the relationship is database-enforced.
* Whether the relationship exists only by naming convention.
* Whether records can become orphaned.

Analyze:

* `ON DELETE CASCADE`
* `ON DELETE SET NULL`
* `ON DELETE RESTRICT`
* Default PostgreSQL delete behaviour
* Generated columns
* Check constraints
* Unique constraints
* Partial indexes
* Database triggers
* Timestamp triggers
* Soft-delete fields
* Polymorphic references

* `EntityType`
* `EntityId`
* `ReferenceType`
* `ReferenceId`

* `RecordId`
* `ModuleType`

# 7. Impact Classification

Classify every identified effect as one of the following.

## DATABASE-AUTOMATIC

PostgreSQL guarantees the effect because of:

* Foreign-key cascade.
* Foreign-key set-null rule.
* Generated column.
* Check constraint.
* Unique constraint.
* Trigger.
* Stored procedure.

## APPLICATION-REQUIRED

The backend must implement the effect through:

* Controller.
* Service.
* Repository.
* API.
* Event handler.
* Queue worker.
* Scheduled job.
* Transaction function.

## APPROVAL-REQUIRED

The operation must remain pending until an authorized approver approves it.

## PERMISSION-DENIED

The user does not have the required role, permission, scope, ownership, or warehouse access.

## REPORTING-ONLY

The source records do not change, but reports, dashboard totals, search results, or analytics are affected.

## POSSIBLE-RISK

The schema implies that a change should occur, but the required constraint or application logic is missing or unclear.

## NO-EFFECT

The table or record should not be changed by the requested operation.

# 9. Inventory Calculation

For each affected product and warehouse, show:

* Product ID.
* Product code.
* Warehouse ID.
* Batch ID.
* Serial numbers.
* Quantity before.
* Reserved quantity before.
* Available quantity before.
* Quantity added.
* Quantity deducted.
* Quantity reserved.
* Quantity released.
* Quantity after.
* Reserved quantity after.
* Available quantity after.

Use formulas such as:

`New physical quantity = old physical quantity + incoming quantity - outgoing quantity`

`New reserved quantity = old reserved quantity + newly reserved quantity - released quantity`

`New available quantity = new physical quantity - new reserved quantity`

Validate:

* Physical quantity must not become negative.
* Reserved quantity must not become negative.
* Reserved quantity must not exceed physical quantity.
* Batch quantity must not become negative.
* Serial-number count must support the transaction quantity.
* Source and destination transfer quantities must balance.
* Product-level total must match the sum of warehouse stock when global stock is maintained.

# 10. Business Workflow Analysis

## 10.1 Purchase requisition

Possible workflow:

* Draft.
* Submitted.
* Pending Approval.
* Approved.
* Rejected.
* Converted to Purchase Order.
* Cancelled.

Stock effect:

Normally none.

Access rules:

* Requester may create and submit.
* Department manager may approve.
* Purchase team may convert an approved requisition.
* Requester should not approve their own requisition when segregation of duties applies.

## 10.2 Purchase order

Possible workflow:

* Draft.
* Pending Approval.
* Approved.
* Sent to Supplier.
* Partially Received.
* Received.
* Closed.
* Cancelled.

Stock effect:

Creating or approving a purchase order normally does not increase physical stock.

Receiving through a GRN should increase stock.

Access rules:

* Purchase Executive may create.
* Purchase Manager may approve.
* Warehouse user may receive.
* Finance user may view financial values.
* Cancellation after receipt requires reversal or return processing.

## 10.3 GRN

Possible workflow:

* Draft.
* Received.
* Partially Received.
* Quality Check.
* Accepted.
* Rejected.
* Cancelled.

Stock effect:

Determine whether stock increases:

* At physical receipt.
* After quality acceptance.
* Only after GRN approval.

Recommended rule:

Accepted quantity increases usable stock.

Rejected quantity should not increase usable stock.

Access rules:

* Warehouse Operator may enter receipt.
* Warehouse Manager may confirm receipt.
* Quality Controller may accept or reject.
* Purchase user may view but should not directly modify warehouse stock.

## 10.4 Purchase return

Possible workflow:

* Draft.
* Pending Approval.
* Approved.
* Dispatched.
* Completed.
* Cancelled.

Stock effect:

Stock should reduce when goods physically leave the warehouse, not simply when a draft return is created.

Access rules:

* Warehouse or purchase user may create.
* Authorized manager approves.
* Warehouse user dispatches.
* Finance team processes supplier credit separately.

## 10.5 Sales quotation

Possible workflow:

* Draft.
* Sent.
* Accepted.
* Rejected.
* Expired.
* Converted.

Stock effect:

Normally no physical stock change.

Optional reservation should occur only if the business explicitly supports quotation-level reservation.

## 10.6 Sales order

Possible workflow:

* Draft.
* Pending Approval.
* Confirmed.
* Processing.
* Partially Dispatched.
* Shipped.
* Delivered.
* Cancelled.

Possible stock policies:

Policy A:

Reserve stock when the order is confirmed and deduct stock when dispatched.

Policy B:

Deduct stock only when dispatched.

The analysis must identify which policy is implemented.

Access rules:

* Sales user creates.
* Sales Manager approves discounts.
* Warehouse user dispatches.
* Sales user cannot directly reduce warehouse stock.
* Cancellation must release reservations.
* Cancellation after dispatch requires a return or reversal.

## 10.7 Delivery challan

Possible workflow:

* Draft.
* Pending.
* Dispatched.
* In Transit.
* Delivered.
* Partially Delivered.
* Cancelled.

Stock effect:

Usually deduct or move stock when dispatch is confirmed.

Do not deduct stock twice if the sales-order workflow already deducted it.

## 10.8 Sales return

Possible workflow:

* Requested.
* Pending Approval.
* Approved.
* Received.
* Inspected.
* Restocked.
* Rejected.
* Refunded.
* Closed.

Stock effect:

Returned stock should increase usable stock only after receiving and inspection.

Damaged returned stock should be recorded separately.

## 10.9 Stock transfer

Possible workflow:

* Draft.
* Requested.
* Approved.
* Dispatched.
* In Transit.
* Partially Received.
* Received.
* Cancelled.

Recommended stock effect:

At dispatch:

* Reduce source available stock.
* Record transfer-out movement.
* Mark stock as in transit.

At receipt:

* Increase destination stock.
* Record transfer-in movement.
* Update batch and serial warehouse.
* Close transfer when fully received.

Access rules:

* Creator needs transfer-create permission.
* Source approver needs approval permission.
* Source warehouse user needs dispatch permission.
* Destination warehouse user needs receive permission.
* The same user should not approve, dispatch, and receive high-value transfers without an exception.

## 10.10 Stock adjustment

Possible workflow:

* Draft.
* Submitted.
* Pending Approval.
* Approved.
* Applied.
* Rejected.
* Cancelled.

Stock effect:

Apply stock only after approval or final posting.

Access rules:

* Operator may enter physical count.
* Warehouse Manager may review.
* Inventory Manager may approve.
* High-value or large-quantity adjustments may require Company Administrator approval.
* The creator should not approve their own adjustment.

## 10.11 Production

Possible workflow:

* Planned.
* Approved.
* Released.
* In Progress.
* Partially Completed.
* Completed.
* Closed.
* Cancelled.

Stock effect:

* Raw materials decrease when issued or consumed.
* Finished goods increase when production output is accepted.
* Rejected production may move to damaged or scrap stock.
* Wastage must be recorded.

Access rules:

* Production user manages operations.
* Inventory user manages material issue.
* Quality user accepts output.
* Production Manager closes the order.

# 20. Mandatory Analysis Rules

Follow these rules strictly:

1. Never assume a role has access based only on the role name.
2. Verify permissions, company scope, branch scope, warehouse scope, ownership, assignment, and visibility.
3. Deny access by default.
4. Do not trust `CompanyId`, `BranchId`, `WarehouseId`, `CreatedBy`, `UpdatedBy`, approval fields, or stock values supplied directly by the frontend.
5. Obtain security-sensitive values from the authenticated server-side context.
6. Do not allow users to change their own role or permissions.
7. Do not allow users to approve their own high-risk transaction.
8. Do not allow warehouse users to modify another warehouse’s stock.
9. Do not allow users to update generated columns directly.
10. Do not allow direct edits to finalized stock transactions.
11. Use reversal transactions instead of deleting posted records.
12. Create an audit log for every privileged action.
13. Use database transactions for all multi-table operations.
14. Use row locks for stock modifications.
15. Prevent duplicate posting through idempotency controls.
16. Mask personal, salary, bank, tax, and financial data for unauthorized roles.
17. Never report an effect as automatic unless the supplied schema guarantees it.
18. Mark missing foreign keys and missing synchronization logic as risks.
19. Clearly distinguish physical stock, reserved stock, available stock, in-transit stock, damaged stock, and rejected stock.
20. Finish with a clear ALLOWED, APPROVAL REQUIRED, or DENIED decision.

* Read and unread behavior.
* Unauthorized users cannot read another user’s notifications.

## 26. Transaction rollback testing

Force failures after intermediate steps.

Examples:

* Fail after stock update but before stock movement.
* Fail after batch update but before audit log.
* Fail after source transfer deduction but before destination receipt.
* Fail after GRN creation but before warehouse-stock update.
* Fail after dispatch but before sales-order update.

Verify that all changes roll back together.

There must not be partially posted stock operations.

## 27. Concurrency testing

Send simultaneous requests for:

* Sales-order confirmation.
* Delivery dispatch.
* GRN receipt.
* Stock adjustment.
* Stock transfer.
* Purchase return.
* Sales return.
* Production consumption.

Verify:

* Stock does not become negative.
* Reserved quantity does not exceed physical quantity.
* The same document is not posted twice.
* Row locking or atomic updates prevent race conditions.
* One request succeeds and conflicting requests fail safely.

## 28. Idempotency testing

Submit the same posting request multiple times using the same request or idempotency key.

Test:

* GRN posting.
* Dispatch.
* Transfer dispatch.
* Transfer receipt.
* Return posting.
* Stock adjustment.
* Production completion.
* Payment creation.

Verify that repeated requests return the existing result and do not duplicate stock, payments, movements, audit logs, or notifications.

1. Do not say a feature works only because the code exists.
2. Verify the actual API response and database result.
3. Do not mark untested behavior as passed.

5. Mark tests that cannot run as `BLOCKED`.

7. Use a separate test database.
8. Do not delete or modify production data.
9. Do not hide failed tests.
10. Do not automatically declare the system production-ready.
11. A critical security, stock, isolation, transaction, or concurrency failure means the system is not production-ready.
12. Fix only simple test-environment or syntax issues when necessary to continue testing.
13. Do not make large architectural changes during testing.
14. Record recommended fixes separately.
15. Run the complete test suite again after any permitted fix.
